# Critique: TARTAR BMS — whole system (deep)

Audited 2026-10-03 on branch `mobile-app-native-newlook` at Development v2.43.

**Scope & assumptions:** the whole repo — client (`src/`), Supabase migrations 1–30, the `send-push`
Edge Function, the service worker, build and deploy config. Read-only.

**Coverage:** code and schema read directly; `yarn lint` and `yarn build` run (both clean).
NOT verified at runtime: no browser, no device, no database access — every UX, mobile, accessibility
and row-count claim below is from code only. Migrations were read in full for auth (22) and by pattern
search for the rest (policies, grants, `security definer`); the payment and voucher RPC bodies were not
re-audited line by line (the roadmap records concurrency tests C1–C5 against them). Supabase dashboard
settings (Auth signups, API max rows) are not in the repo and are listed under Hypotheses.

## Executive summary

The codebase is disciplined: both gates are clean, the house rules hold with no exceptions outside the
generated `components/ui` (no `useState`, no `any`, no comments, no inline styles but one), and the
offline write queue is carefully built. The real risks are elsewhere. (1) Account security rests on a
home-made login whose password reset can be requested by anyone for any account and whose login has no
attempt limit. (2) Money totals on the dashboard, party summaries and reports are summed in the browser
from unpaged reads, so they silently go wrong once a table passes the API row cap. (3) The hand-rolled
query cache has no request ordering and refetches far more than is on screen. (4) There are no automated
tests on the money math. Fix the read-completeness bug first: it produces wrong numbers without any error.

## High-priority findings

### [SEC-01] Anyone can stage a new password for any approved account
**Category:** Security · **Severity:** High · **Confidence:** High · **Basis:** FACT (mechanism) + RISK (takeover)

**What I found** — `request_password_reset(p_email, p_password)` is granted to `anon`. It writes
`pending_password_hash` for any approved account, with no proof the caller owns it. An admin then
approves it from the Users table, which shows only a "Reset requested" tag and a confirm that reads
"Their old password stops working; they sign in with the one they requested."
**Evidence** — `supabase/migrations/20261010000022_admin_branch_scope.sql:623-647` (function),
`:721` (grant to anon), `:649-673` (`decide_password_reset`); `src/hook/data/user/user.manage.hook.ts:213-227`
(confirm copy); `src/components/user/tables/UsersTable.tsx:49-51`. `account_email_exists` (`:612-621`,
granted to anon `:720`) tells the caller which emails are real.
**Why it matters** — An outsider who knows a staff email submits their own password; one routine
admin click hands them the account. The same call overwrites a genuine pending request.
**User impact** — A manager or accountant account can be taken over; the real user is locked out.
**Technical impact** — No audit trail of who requested or approved a reset.
**Recommended direction** — Smallest first: make the approval confirm say when the request was made and
that the admin must confirm it with the person directly (client only). Proper fix (migration, user
approval): drop the anon-supplied password — approval issues a one-time temporary password the admin
hands over, or the admin sets it with the existing `admin_set_password`.
**Verification** — Signed out, call `rpc/request_password_reset` with a known staff email; the Users
table shows "Reset requested" for that user. After the fix the anon call must not stage a usable password.

### [DATA-01] Dashboard, party and report totals are summed from unpaged reads and truncate silently
**Category:** Database / API · **Severity:** High · **Confidence:** Medium (cap value not in repo) · **Basis:** FACT (code) + RISK (wrong totals)

**What I found** — Aggregates fetch raw rows with no range and add them up in the browser. PostgREST
returns at most the project's max rows (Supabase default 1,000) and reports no error when it cuts off.
Reports add `.limit(5000)`, which is also a silent cap and is itself bounded by the server maximum.
**Evidence** — `src/services/data/dashboard.services.ts:177-201` (`outstandingOf`, `createdSince`),
`:204-281` (`getSummary`, whole month), `:283-319` (`getOverview`, period "all" = every sale and expense),
`:321-354` (`getSalesSeries`, up to 5 years), `:356-412` (`getBranchMonitor`, all time, four tables),
`:461-489`; `src/services/data/ledger.services.ts:52`, `:90-106`, `:108-150`, `:207-242`;
`src/services/data/transaction.services.ts:56`, `:207-217`, `:293-304`.
**Why it matters** — This is a bookkeeping system. Past the cap, receivable/payable balances, monthly
sales and printed reports are understated with nothing on screen to say so.
**User impact** — Owners read and print wrong totals and cannot tell.
**Technical impact** — Every new aggregate copies the pattern; payload grows with history.
**Recommended direction** — Now, without a schema change: one shared "fetch every page" helper (stable
order, `.range()` until a short page) used by every aggregate and report read, replacing the 5,000 cap.
Later (migration, user approval): server-side aggregate RPCs so totals do not ship rows at all.
**Verification** — `select count(*)` on transactions/receivables for one branch; if any aggregate's
filter matches more than the API max rows, compare the dashboard figure with `select sum(...)`.

### [SEC-02] Login has no attempt limit and a 6-character minimum
**Category:** Security · **Severity:** High · **Confidence:** High · **Basis:** FACT + RISK

**What I found** — `login_email` is callable by `anon`, checks a bcrypt hash and raises on failure; nothing
counts or delays failed attempts. Password rules are length ≥ 6 only.
**Evidence** — `supabase/migrations/20261010000022_admin_branch_scope.sql:558-610`, `:480`, `:418`, `:694`;
no match for attempt/lockout/rate-limit in any migration.
**Why it matters** — With SEC-01's email check, an attacker can guess passwords in parallel; bcrypt slows
each guess but nothing stops the stream.
**Recommended direction** — Migration (user approval): a failed-attempt counter with a short lockout per
account, and a longer minimum length for new passwords. Supabase's own rate limits do not cover RPCs.
**Verification** — 50 wrong-password calls in a loop all return 28P01 with no slowdown.

## Security findings

### [SEC-03] No security headers on the deployed app
**Severity:** Medium · **Confidence:** High · **Basis:** FACT
`vercel.json` contains only the SPA rewrite — no Content-Security-Policy, no frame protection, no
`nosniff`, no referrer policy. The session token is in `localStorage` (`account.store.ts:62-68`), so a
script injection reads it directly; a CSP is the standing defence. **Direction:** add `headers` to
`vercel.json`: `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`, `Permissions-Policy`,
and a CSP in report-only mode first (self + the Supabase origin over https/wss + fonts), enforced once the
preview console is clean. **Verification:** `curl -I` the preview URL.

### [SEC-04] Low · FACT — Search text reaches `ilike` unescaped
`src/utils/filter.utils.ts:42-45`. `%` and `_` typed by a user act as wildcards (a search for `_` matches
everything). Not injection; escape the three pattern characters before building the pattern.

### [SEC-05] Low · FACT — `send-push` hides delivery failures
`supabase/functions/send-push/index.ts:72-77`, `:119-122`: any failure other than 404/410 is swallowed and
still counted in `sent`. The secret is compared with `!==` (not constant-time). Count failures separately.

## QA findings

### [QA-01] A slower, older response can overwrite a newer one in the query cache
**Severity:** Medium · **Confidence:** High · **Basis:** FACT (no ordering) + RISK (stale screen)
`src/store/common/query.store.ts:68-129`: `run` has no request token and no in-flight sharing. Mount,
realtime invalidation, post-sync `refetchAll` and pull-to-refresh can all start fetches for one key; the
last to *finish* wins. **Impact:** after approving or paying, a list can flip back to the old row until the
next refresh. **Direction:** a per-key sequence number — only the newest request may write — and share an
in-flight promise for the same key. **Verification:** throttle the network, trigger two refetches of one
key with different server state; the older must not land.

### [QA-02] Low–Medium · RISK — A queued edit that actually saved is reported as a conflict
`update_transaction_with_voucher` is queued through `runWrite` (`transaction.services.ts:360-387`) but is
not in `idempotentRpcs` (`write.utils.ts:12-21`). If the response is lost after the server commits, the
replay meets a bumped version and lands in the failed list as "someone else changed this record".
Needs a server-side idempotency key (migration) — an Open item, not a client fix.

### [QA-03] Low · FACT — A throwing `onSuccess` turns a saved write into an error
`src/hook/common/mutation.hook.ts:32-60`: `onSuccess` runs inside the same `try` as the write, after the
success toast. If it throws, the user sees success then an error and may save twice. Run it outside the
write's failure path.

## Performance findings

### [PERF-01] Every realtime event refetches every list variant seen this session
**Severity:** Medium · **Confidence:** High · **Basis:** FACT
`query.store.ts:44` keeps a fetcher for every key ever run and never prunes it; `invalidate` (`:161-180`)
and `refetchAll` (`:182-184`) rerun all of them, mounted or not. `hook/app/realtime.hook.ts:21-27` calls
`invalidate` for each live key on every change. After browsing with search, filters and growing page
windows, one change by any user triggers dozens of full list queries. **Direction:** refetch only watched
keys plus the primed offline set; drop fetchers for unwatched paged/search variants (they refetch on
mount anyway). Keep `prime` working — offline freshness depends on it.

### [PERF-02] The offline query cache is never trimmed
**Severity:** Medium · **Confidence:** High · **Basis:** FACT
`query.store.ts:103` writes every key to IndexedDB; `idb.utils.ts:30-39` loads all of it into memory at
start. Keys include search text, filters and page size, so entries accumulate until sign-out.
**Direction:** on hydrate, drop entries past an age or count bound; never persist search-term variants.

### [PERF-03] Entry chunk is 1.29 MB (389 kB gzip)
**Severity:** Medium · **Confidence:** High · **Basis:** FACT
`yarn build`: `index-*.js 1,290.58 kB │ gzip 388.80 kB`; precache 88 entries, 2.76 MB;
`vite.config.ts` has no chunking config. First visit on a phone over 3G pays all of it before sign-in.
**Direction:** inspect what the entry pulls in (the sign-in page should not need the app shell), then
split vendors and defer what the login route does not use. Measure before and after.

## Testing

### [TEST-01] No automated tests; the only gate is that it compiles
**Severity:** Medium · **Confidence:** High · **Basis:** FACT
No test files, no test script, no CI. Pure, money-bearing logic is untested: `utils/voucher.utils.ts`
(VAT and withholding), `utils/report.utils.ts` (430 lines), `utils/disbursement.utils.ts`,
`sumCounted`, and the replay rules in `utils/write.utils.ts`. **Direction:** a unit runner for the pure
utils only (vitest fits Vite with no config); characterise current behaviour, change no rule.

## Positive findings

- Both gates clean; zero rule breaches found by search outside generated code.
- Offline queue: stamped ids make inserts replay-safe, idempotency keys on eight RPCs, optimistic
  `version` on updates, owner-scoped entries that survive sign-out, a Web Locks guard across tabs
  (`write.utils.ts`, `sync.store.ts`).
- Authorization is read from the `users` table on every request, not from JWT claims
  (`migration 22:78-88`), so revoking a user or a branch takes effect immediately.
- All 82 `security definer` functions pin `search_path`; RPC grants are revoked from `public` first.
- Sign-out clears the query cache and resets every store (`account.logout.hook.ts:14-21`).
